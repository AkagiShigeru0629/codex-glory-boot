# Codex 荣耀零等待启动设计

> **历史说明：** 冷启动“立即显示首帧”的显示时机已于 2026-11-12 被第二阶段设计改为等待 Codex 主窗口稳定后再显示和播放。其余媒体时间线、停留、超时和交接规则继续有效。

**状态：** 已批准，视觉方向修订于 2026-11-04，本地样片迭代于 2026-11-05，媒体契约同步于 2026-11-06，最终时间重排于 2026-11-07

## 意图

为 Windows 版 Codex 制作一个全 Python 的独立启动器。用户点击专用入口后，启动器立即显示首帧海报并播放荣耀主题动画，同时 Codex 在后台启动；动画结束通过桌面窗口管理器（DWM）交接给真实窗口。

项目同时承担求职展示用途，因此需要清晰分层、类型注解、自动化测试、可观测性和可解释的 Windows 原生适配，而不仅是可运行的脚本集合。

## 目标

- 启动器运行时和开发工具链全部使用 Python。
- 点击后 800 毫秒内显示首个可见画面；目标值需在打包版本中实测。
- 首帧显示与 Codex 启动并行，不等待 Codex 页面或主窗口。
- 当前正式成片总长由配置决定；启动器不将固定时长写死为领域层约束。Codex 窗口框架连续稳定后，动画始终连续播放到结束，不等待页面内容加载。
- DWM 成功时平滑展示真实 Codex，失败时淡出回退。
- `Esc` 跳过、媒体失败、激活失败和超时均能安全退出。
- 使用 PyInstaller onedir 打包，避免 onefile 解压延迟。
- 不修改 Codex 安装文件，不创建常驻服务或开机自启。

## 非目标

- 第一阶段不实现 Codex 内部用户界面（UI）皮肤。
- 不实现动画在线编辑、远程下发或云服务。
- 不保证接管 Windows 搜索、协议链接和第三方程序的启动入口。
- 不决定项目整体开源许可证。
- 不通过 C#、Node.js 或外部播放器承担产品业务逻辑。

## 反目标

- 点击后先等待 Codex 页面，再开始播放动画。
- 使用 PyInstaller onefile 导致每次启动先解压。
- 用户界面线程同步等待主窗口或外部进程。
- 用页面内容、日志标记或壁纸加载状态暂停和延长开屏动画。
- 为隐藏问题而无限暂停。
- 把 Win32、Qt 和业务状态混在单个文件里。

## 已考虑的方案

### 方案 A：C# WPF + MP4 + DWM

首帧快、依赖少，但不满足全 Python 和求职展示目标。**不采用。**

### 方案 B：Python + PySide6 + QtMultimedia + DWM

产品代码全部 Python；PySide6 负责窗口和视频，`ctypes` 负责 Win32/DWM；PyInstaller onedir 打包。首帧目标需从 300 毫秒放宽到约 800 毫秒，但可以保留“先显示、后等待、全程并行”的零等待体验。**采用。**

### 方案 C：Python + Tkinter + 外部播放器

依赖最少，但视频播放、窗口合成和 DWM 行为不够可控，桌面兼容性差。**不采用。**

## 技术栈

- CPython 3.14
- PySide6 6.12
- QtMultimedia：`QMediaPlayer`、`QAudioOutput`、`QVideoWidget`
- `ctypes`：Win32、DWM、DPI、窗口与进程路径查询
- `QProcess`：非阻塞启动 Codex
- `QTimer`：250 ms 窗口探测和媒体状态驱动
- `dataclasses` + `json`：配置模型
- `logging`：结构化文本日志
- pytest：自动测试
- Pillow、NumPy、imageio-ffmpeg：视频生成
- PyInstaller onedir：打包

## 视觉设计

- 当前正式成片画幅为 1920×1080、60 帧、8.0 秒；时长和关键时间点可在新的媒体版本中调整，但必须与配置、设计说明和媒体规格测试同步。
- 不出现人物或现成游戏截图，采用纯代码绘制的“荣耀”游戏开场界面。
- 参考动画第二季官方 UI 示例提炼黑玻璃面板、细金属边框、四角饰件、金色分区标题和克制的能量光，不复刻原作界面或素材。
- 中央：自绘圆形荣耀徽记，由刻度环、翼状弧线和对称刃形组成，分段组装后点亮。
- 背景：深炭黑与墨绿烟雾渐变、低对比度金属刻线和缓慢移动的暗金流光，不使用大面积冰蓝。
- 色板：炭黑和墨绿为主体，旧金与象牙白承担标题和边框，青蓝只用于少量能量脉冲，橙金和荧光绿用于状态反馈。
- 状态区域：底部以游戏登录界面式横条显示“荣耀”和 Codex 启动状态；“确定”和“返回”作为不可交互的装饰性登录控件保留。
- 转场：中央屏幕区域扩大，真实 Codex 从中央显现并铺满。

### 时间线

| 时间 | 内容 |
| --- | --- |
| 0.0–0.8 秒 | 固定尺度的首帧海报和柔和起亮 |
| 0.8–4.9 秒 | 压缩后的七阶段主画面动效 |
| 4.9–5.2 秒 | 红色扫描与亮度桥接进入登录界面 |
| 5.2–6.4 秒 | “荣耀丨codex”标题进入并完成读清 |
| 6.4–7.1 秒 | CRT 压线、亮点熄灭 |
| 7.1–7.6 秒 | DWM 在整窗矩形内淡入真实 Codex |
| 7.6–8.0 秒 | 启动器退出，Codex 获得输入 |

### 本地样片迭代（2026-11-05，最终重排于 2026-11-07）

- 使用本地素材 `glory1.mp4` 的荣耀主画面推进到约 4.9 秒，在 4.9–5.2 秒通过红色扫描和亮度混合进入登录界面。
- 5.2–8.0 秒使用 `glory.mp4` 中约 0.48–1.56 秒的十区画面并重采样到约 2.8 秒，使结尾获得完整展示和停留。
- “确定”“返回”“荣耀十区”和其他底部 HUD 保留原素材内容，不因 Codex 启动流程删除或替换。
- 前段只在 0.8–2.4 秒进行一次不超过 2.5% 的缓慢靠近，2.4 秒后固定构图，不再重复推拉或漂移。
- 结尾标题保留静态点阵和扫描纹理，不持续叠加随机横向错位故障，避免等待帧冻结在花屏状态。
- 前 0.8 秒锁定画面尺度并柔和亮起，消除源片开头的整体扩大感；其后按粒子汇聚、环形校准、双段光刃、数字故障、能量爆发、纵向扫描锁定和蓄力交接七个阶段推进，同时用推进与回拉的镜头段落建立节奏，避免长时间重复同一种红色扫描效果。
- 十区中央标题改写为“荣耀丨codex”，限制在背景中央框的安全区域内，以方块字形、细红描边、暗色内芯、扫描纹理、稀疏点阵高光、辉光和故障切片贴近原有界面风格。
- 成片不保留原 Codex 标识黑屏结尾；CRT 收束后由 DWM 在整窗矩形内淡入真实 Codex。
- 该样片只使用秋月大人的本地素材；正式 `media/startup.mp4` 和 `media/poster.png` 已替换，发布包仅供本地个人版本使用，公开分发前仍需替换或取得授权。

## 架构

### 纯领域层

- `glory_boot/domain/models.py`：不可变配置、窗口矩形和屏幕关键帧。
- `glory_boot/domain/timeline.py`：停留、恢复、过渡和超时状态机。
- `glory_boot/domain/geometry.py`：物理像素、DPI、显示器与客户区换算。
- `glory_boot/domain/policy.py`：媒体、DWM、激活失败和超时的交接决策。

领域层不导入 PySide6、`ctypes`、`subprocess` 或文件系统。

### 服务层

- `glory_boot/services/codex_launcher.py`：使用 `QProcess` 请求 Codex 启动，复用已有窗口，并在明确的激活失败后允许受控重试。
- `glory_boot/services/window_probe.py`：定时查询已存在的 Codex 主窗口并判断就绪。
- `glory_boot/services/media.py`：封装 `QMediaPlayer` 的打开、暂停、恢复和首帧信号。
- `glory_boot/services/session.py`：编排海报、动画、Codex 启动、等待和交接。
- `glory_boot/services/logging.py`：结构化启动时间线日志。

### 平台层

- `glory_boot/adapters/win32.py`：`EnumWindows`、窗口样式、进程路径、DPI 和置顶。
- `glory_boot/adapters/dwm.py`：缩略图注册、更新和释放。
- `glory_boot/adapters/shell.py`：快捷入口和恢复。

所有 P/Invoke 参数类型、结构和错误码集中定义，业务层不直接调用 Win32。

### 用户界面层

- `glory_boot/ui/boot_window.py`：无边框窗口、海报、视频容器、跳过按钮和错误提示。
- `glory_boot/ui/application.py`：QApplication 生命周期、单实例和异常兜底。

## 启动流程

1. `main.py` 记录进程启动时间，创建 QApplication。
2. 读取并校验配置，立即创建窗口和海报控件。
3. `show()` 后记录首个可见窗口时间。
4. 启动 `QMediaPlayer`，异步设置视频源。
5. 通过 `QProcess` 发送首次 Codex 启动请求；请求返回失败时等待 1 秒重试，请求看似成功但 8 秒内仍无主窗口时再次激活，总计最多三次。
6. Codex 主窗口连续两个探测周期稳定后，视为窗口框架就绪并开始动画。
7. 动画时间线连续播放，页面内容、日志挂载标记和壁纸加载状态都不触发暂停。
8. 进入交接区间后在整窗矩形内更新 DWM 缩略图。
9. 播放位置到达 `duration - 50 ms` 时主动暂停在最后有效帧，保留 0.2 秒后交接。
10. 交接时聚焦可用 Codex 窗口，再关闭启动器；无法使用 DWM 时执行窗口淡出回退。

## 窗口框架就绪规则

Codex 主窗口必须同时满足：

- 进程名属于配置白名单；
- 可执行路径包含 `OpenAI.Codex_`；
- 顶层的 `Chrome_WidgetWin_1`；
- 可见、未被桌面窗口管理器标记为隐藏、不是工具窗口；
- 客户区至少 450×280；
- 连续两个探测周期可响应。

这是窗口可用性的工程判断，不是页面内容加载完成回调。页面后续加载耗时由
Codex 自身承担，不再阻塞开屏动画。

## 故障处理

- Codex 已在运行：不重复启动，直接复用。
- Codex 刚结束或 Windows Shell 暂时忽略激活请求：允许在窗口未出现时受控重试；Codex 主界面就绪后立即停止重试，避免重复启动。
- 媒体缺失或损坏：记录错误，立即交接或打开 Codex。
- 播放器到达 `EndOfMedia` 后可能清空视频表面：在播放位置到达 `duration - 50 ms` 时提前暂停，避免进入会清空画面的结束状态。
- DWM 注册或更新失败：停止使用缩略图，淡出启动器窗口。
- Codex 激活失败：显示简短错误并退出，不阻塞桌面。
- 超过 `MaxWaitSeconds`：执行超时回退，不在等待画面上无限停留。
- 多个启动器实例：使用 Windows 命名互斥量阻止第二个实例。

## 可观测性

日志记录以下单调时钟阶段，不记录窗口标题、截图或用户内容：

- `process_start`
- `qt_ready`
- `window_visible`
- `media_requested`
- `media_first_frame`
- `codex_launch_requested`
- `codex_launch_accepted`
- `codex_launch_reused`
- `codex_launch_failed`
- `codex_launch_retry`
- `codex_window_found`
- `codex_stable`
- `target_frame_ready`
- `handoff_complete`

每个阶段同时写入从进程启动开始的毫秒数。

## 验收

- `.venv` 中可在 Windows 10/11 x64 运行全部 pytest。
- PyInstaller onedir 包可启动，首帧目标 800 ms 并记录实测值。
- Codex 与动画并行启动。
- Codex 页面内容晚于开屏动画时，动画仍连续播放并按时消失。
- 多显示器、DPI、非 16:9 和负坐标定位正确。
- DWM、媒体、激活失败均有安全回退。
- 专用入口可安装和恢复，Codex 安装目录未改变。
