# Codex 荣耀启动器第二阶段设计

**状态：** 待秋月大人审核

## 意图

第一阶段已经完成独立启动器、荣耀开屏动画、并行启动 Codex 和桌面窗口管理器（Desktop Window Manager，DWM）交接。第二阶段继续增强视觉连续性，但保持第一阶段已经验证的启动时序和领域状态机不变。

第二阶段分成两个互不依赖的子项：

- **第二阶段 A：启动器窗口适配。** 让独立启动器按照 Codex 主窗口的客户区显示动画，不再始终铺满整块屏幕。
- **第二阶段 B：Codex 内部壁纸。** 在不修改 Codex 安装目录的前提下，把本地壁纸放到 Codex 原生界面下方，并确保菜单、弹窗和输入区域仍然清晰可用。首版只处理壁纸与必要的背景透明度，不重做完整用户界面皮肤。

两个子项共享视觉目标，但采用不同技术路线。窗口适配不得依赖调试端口，内部壁纸的失败也不得影响正常启动 Codex。

## 目标

- 第一阶段的首帧目标、并行启动、自适应等待、超时回退和 DWM 交接继续有效。
- 第二阶段 A 在已知 Codex 目标窗口后，让动画、等待画面和最终交接使用同一套目标几何。
- 第二阶段 A 支持多显示器、负坐标、125%／150% 等常见 DPI 和最大化窗口。
- 第二阶段 B 将壁纸放在 Codex 原生内容下方，不改变点击、输入、聊天和弹窗操作。
- 第二阶段 B 可以检测兼容性、主动关闭并在运行中或重启后恢复官方外观。
- 第二阶段 B 首版只验证壁纸效果和日常可用性，为是否继续开发完整皮肤提供实际依据。
- 所有产品编排、窗口适配和恢复逻辑继续使用 Python。
- 不修改 Microsoft Store 版 Codex 的安装文件或用户数据。

## 非目标

- 不把启动动画注入 Codex 页面；第一阶段动画仍由独立启动器播放。
- 不在第二阶段 A 中持续跟随 Codex 窗口拖动或缩放。
- 不在第二阶段 B 中读取、记录或修改聊天内容、账号信息、输入内容和页面文字。
- 不提供远程配置、在线主题下载、云同步或常驻服务。
- 不替换 Codex 的官方协议入口、搜索入口或安装包。
- 不承诺对未经验证的未来 Codex 版本自动兼容。
- 不增加开机自启、后台监控或自动升级能力。
- 不在本阶段实现壁纸编辑器和完整的桌面美化系统。
- 第二阶段 B 首版不重新设计按钮、字体、图标、布局和交互控件。
- 没有实际使用反馈或明确建议时，不扩展完整 Codex 用户界面皮肤。

## 反目标

- 为了等待 Codex 主窗口而延迟首帧海报。
- 让窗口适配失败阻断 Codex 启动或 DWM 回退。
- 把全屏状态、主显示器坐标或 100% DPI 写死到新逻辑。
- 将调试端口开放到非回环地址。
- 通过修改 Codex 安装目录实现外观。
- 使用覆盖在 Codex 上方的透明窗口冒充底层壁纸。
- 通过读取页面文字判断壁纸是否生效。
- 让窗口适配和内部壁纸互相成为启动前提。
- 把已知不兼容的版本静默注入后继续运行。

## 约束

- 第一阶段设计中的启动流程、时间线、等待策略和故障回退保持不变。
- 产品业务逻辑、测试和 Windows 适配使用 Python。
- 用户界面与媒体继续使用 PySide6 6.12 和 QtMultimedia。
- Windows 原生能力通过 Python `ctypes` 封装，包括窗口客户区、DPI、显示器、DWM 和调试端点所有权检查。
- 注入页面中的脚本只承担固定的视觉呈现与撤销，不读取页面内容，不构成独立业务逻辑。
- 不引入 Node.js 或 C# 产品代码。
- 优先使用 PySide6 已有的 Qt WebSocket 能力；只有确有必要时才申请新增依赖。
- `media/`、`assets/local/` 和用户壁纸不得写入日志或上传。
- 所有新增公开函数和方法提供类型注解。
- 第二阶段 A 和 B 分别具备独立测试、独立开关和独立回退路径。

## 方案比较

### 第二阶段 A：窗口适配

#### 方案 A1：将启动动画注入 Codex 页面

动画可以天然继承页面尺寸，但必须等待 Codex 渲染器存在，直接破坏“先显示海报、并行启动”的核心体验，也把第一阶段耦合到 Codex 内部结构。**不采用。**

#### 方案 A2：独立启动器按 Codex 客户区对齐一次

启动器继续独立运行；Codex 主窗口稳定出现后，读取其客户区和所在显示器，重新定位并调整启动器几何。动画、等待层和 DWM 交接共用该矩形。**采用。**

该方法保留第一阶段时序，同时避免持续跟随窗口带来的抖动、拖动冲突和额外轮询。

#### 方案 A3：使用固定的默认窗口或主显示器全屏

实现最简单，但在多显示器、不同 DPI 和用户自定义窗口尺寸下仍然突兀，也无法真正验证 Windows 几何适配能力。**不采用。**

### 第二阶段 B：内部壁纸

#### 方案 B1：外部透明窗口覆盖 Codex

可以实现边框和装饰层，但无法把壁纸放到 Codex 不透明内容的下方。覆盖层还会影响点击命中、拖动、截图和可访问性。**不采用。**

#### 方案 B2：修改 Codex 安装目录

可以深度修改界面，但应用更新会覆盖，恢复困难，并扩大安全和许可风险。**不采用。**

#### 方案 B3：通过本地调试协议注入固定样式

在 Codex 页面内加入固定样式表，使原生根容器和内容表面透明，把壁纸设置为页面底层背景；必要的菜单、输入框和弹窗保持不透明。无需修改安装目录，并可在页面内撤销。**采用。**

#### 方案 B4：仅设置 Windows 桌面壁纸

稳定但只能显示在 Codex 窗口外部，无法形成应用内视觉延续。**不采用。**

## 第二阶段 A：启动器窗口适配

### 启动原则

首帧显示不得等待 Codex 窗口。启动器先使用上一次成功交接时保存的 Codex 客户区；首次运行或记录无效时，使用当前光标所在显示器内的安全默认矩形。若该矩形不可用，再回退到当前显示器全屏。

目标 Codex 窗口稳定出现后，只进行一次几何校准：

1. 读取目标窗口的客户区尺寸和屏幕坐标。
2. 将启动器移动到对应显示器，并调整为客户区大小。
3. 海报、视频和等待提示随启动器重新布局。
4. DWM 过渡和最终交接使用同一个目标矩形。

校准完成后不再跟随 Codex 窗口移动或缩放。若目标窗口在校准前发生变化，以最后一次稳定探测结果为准；若之后无法继续取得目标窗口，保留已经校准的几何并执行现有回退路径。

### 几何来源

- 使用 `GetClientRect` 获取客户区宽高。
- 使用 `ClientToScreen` 或等价 Win32 调用把客户区转换为物理屏幕坐标。
- 窗口选择继续使用第一阶段的进程名、包路径、窗口类、可见性、工具窗口样式和响应性条件。
- 目标矩形必须与所在显示器有有效交集；完全离屏的矩形视为无效。
- 保存几何时只记录坐标和尺寸，不记录窗口标题、截图或用户内容。

### 首帧与校准

- 首帧目标仍以第一阶段基准为准，不因保存几何的加载而推迟。
- 首次运行的安全默认矩形优先使用当前显示器工作区的约 70% 尺寸，居中显示，并保持可读的最小尺寸。
- 校准只改变已有画面的窗口几何，不重新创建播放器，不重新打开媒体。
- 校准期间不得出现白屏、黑屏或媒体重新起播。
- 若校准导致不可接受的闪烁，允许把校准限制在首个可交互窗口出现前完成；不得用长时间暂停规避问题。

### 失败与回退

- 没有保存几何：使用当前显示器安全默认矩形。
- 记录格式错误、尺寸过小或完全离屏：忽略记录并回退。
- 找不到 Codex 主窗口：继续现有等待和超时流程。
- 几何读取失败：启动器保持当前有效几何，DWM 失败时继续使用窗口淡出。
- 用户跳过动画：不为了等待校准而延迟交接。

### 测试与验收

- 多显示器正坐标、负坐标和不同 DPI 下，启动器与目标客户区一致。
- 最大化、普通窗口和最小客户区尺寸均能取得有效矩形。
- 没有保存几何和记录损坏时，仍有首帧并进入安全回退。
- 校准不会重新创建媒体播放器或重置播放位置。
- DWM 更新和最终交接使用校准后的目标矩形。
- 第一阶段首帧、并行启动、等待、超时和 DWM 回退测试继续通过。

## 第二阶段 B：Codex 内部壁纸

### 模块定位

内部壁纸是可选增强模块，只在用户明确开启时启用。关闭时不创建额外启动参数、不开放调试端口、不启动注入流程，Codex 按第一阶段路径正常启动。

第二阶段 B 不接管启动动画。启动动画结束后，壁纸模块才在已挂载的 Codex 主页面中安装样式。

首版范围只包括：

- 壁纸本身；
- 让壁纸从原生内容后方显示所必需的根容器、侧栏和主内容表面透明度；
- 为保持文字、输入框、代码块、菜单和弹窗可读性所必需的局部背景调整。

首版不包括按钮、字体、图标、间距、布局、动画和交互控件的重新设计。完整界面皮肤必须依据实际使用反馈和建议另立阶段、设计与验收。

### 启动与连接

1. 读取壁纸开关和经过校验的本地壁纸路径。
2. 选择仅绑定 `127.0.0.1` 的随机高位端口，不允许固定暴露到局域网。
3. 使用与 Codex 应用激活方式兼容的 Python 启动后端传入调试参数。
4. 轮询本地 JSON 调试端点，只接受本次启动且进程归属正确的 Codex 页面。
5. 拒绝非 `127.0.0.1`、端口不一致、包含用户名密码或非目标页面地址的 WebSocket 地址。
6. 页面结构符合已登记兼容配置后，再连接并注入固定样式。

端口、进程号和页面目标只用于校验；日志不得记录认证请求头、页面内容或用户壁纸数据。

### 注入内容

注入内容只包括：

- 一个可识别并删除的样式节点；
- 一组明确列出的主题背景变量；
- 壁纸资源地址；
- 记录原始根元素属性和变量的最小状态；
- 固定的检测、启用、关闭和状态查询函数。

样式必须做到：

- 壁纸位于 Codex 页面底层背景。
- 主聊天区域、侧栏和页面根容器按设计使用透明或半透明表面。
- 菜单、对话框、输入框、代码块和浮层保持清晰可读。
- 不设置全局 `pointer-events: none`，不使用覆盖整个页面的不可见元素。
- 不拦截键盘、鼠标、剪贴板或拖放事件。
- 不使用持续动画、滤镜循环或高频背景重绘。

### 可检测

检测分为注入前和注入后。

注入前至少检查：

- 目标页面和路由符合已登记配置；
- 必要的页面根节点存在；
- 必要的主题变量存在；
- 当前 Codex 版本或页面能力命中已登记兼容配置；
- 调试端点属于刚启动的 Codex 进程。

注入后至少检查：

- 样式节点和皮肤标记存在；
- 壁纸背景地址已经应用；
- 核心背景节点命中预期透明规则；
- 注入过程中没有返回脚本异常。

检测失败时不进行第二次盲目注入。模块记录原因码并恢复原生外观。

### 可关闭

关闭入口包括：

- 配置开关关闭；
- 启动参数显式禁用；
- 运行中固定的恢复快捷键；
- 注入失败后的自动关闭；
- Codex 退出或页面重新加载时清理失效状态。

关闭皮肤后不要求重启启动器。若页面已经无法响应恢复指令，则提示完全退出并重新打开 Codex；重启后因为安装目录未被修改，官方外观自然恢复。

### 可恢复

恢复流程必须：

1. 移除注入的样式节点。
2. 撤销壁纸图片地址并释放 Blob URL 或等价临时资源。
3. 恢复注入前的根元素属性。
4. 恢复注入前被修改的 CSS 变量和优先级。
5. 删除页面内的状态对象。
6. 再次检查关键标记已经不存在。

恢复代码不得使用整体清空页面样式的做法，也不得触碰与壁纸无关的页面状态。

### 版本与兼容

兼容性由能力探测和版本记录共同判断：

- 版本号用于选择已登记的样式配置和提示兼容状态。
- 能力探测用于确认当前页面确实具备所需节点和主题变量。
- 版本号命中但能力探测失败时，仍拒绝注入。
- 未登记的新版本默认停用壁纸，不静默尝试未知样式。
- Codex 更新后必须先运行壁纸回归检查，再登记新的兼容配置。

### 隐私与安全

- 调试地址只允许回环地址。
- 只执行项目内置的固定脚本，不接受外部传入的任意脚本。
- 不读取页面文字、聊天、账号、Token、Cookie 或本地存储。
- 不截图，不导出窗口内容。
- 壁纸只从经过校验的本地文件加载。
- 不监听其他应用、不常驻后台、不建立远程连接。
- 调试端口随本次 Codex 进程结束而失效；若端点无法确认由目标进程持有，则终止注入。

### 测试与验收

- 开关关闭时没有调试参数、注入进程或壁纸改动。
- 错误端口、非回环地址、错误进程和错误页面目标均被拒绝。
- 页面结构不匹配时直接回退原生外观。
- 成功注入后壁纸位于页面底层，菜单、弹窗和输入区域保持可用。
- 壁纸不改变鼠标命中、键盘输入、粘贴、滚动和拖放行为。
- 执行恢复后样式节点、壁纸变量和根元素标记全部消失。
- 在可恢复状态下重新注入不会叠加重复样式。
- 无法恢复时，完全重启 Codex 能让官方外观恢复。
- 日志只包含版本、阶段、布尔结果、耗时和错误码，不包含页面内容或壁纸数据。
- 不使用真实的用户聊天内容进行自动测试。

## 第一阶段的兼容边界

- 第二阶段 A 可以替换启动器的目标几何来源，但不得改变海报首绘、媒体请求和 Codex 启动请求的并行关系。
- 第二阶段 B 不得成为第一阶段启动成功的前提。
- 两个子项都不得改变 `domain/` 中与停留、恢复、超时和交接原因有关的状态规则。
- 第一阶段 DWM 失败回退、媒体失败回退、激活失败回退和 `Esc` 跳过继续有效。
- 第二阶段新增配置必须提供安全的默认关闭值，并保持旧配置可读取。

## 交付顺序

1. 完成第二阶段 A 的设计验证和自动化测试。
2. 完成第二阶段 A 的真实多显示器与 DPI 验收。
3. 单独完成第二阶段 B 的注入技术验证，不纳入正式默认路径。
4. 验证检测、关闭、恢复和版本守卫。
5. 第二阶段 B 取得秋月大人的真实 Codex 冷启动验收后，才决定是否默认启用。

## 完成标准

- 第二阶段 A 按 Codex 客户区显示并完成同矩形 DWM 交接，失败时仍可正常回到 Codex。
- 第二阶段 B 仅作为可选增强启用，壁纸位于 Codex 内容下方且不影响操作。
- 第二阶段 B 首版没有改变 Codex 的按钮、字体、图标、布局或交互控件。
- 第二阶段 B 能看到明确的启用、降级和关闭状态。
- Codex 更新、结构不匹配或调试连接失败时，启动器仍能进入原生且可操作的 Codex。
- 完全重启 Codex 后能够恢复官方外观。
- README、执行计划、测试和第三方声明与实际实现同步。
- 提交、替换入口和真实 Codex 验收仍分别取得明确同意。
